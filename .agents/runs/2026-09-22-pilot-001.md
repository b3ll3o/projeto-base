## Aprendizados Chave

### 1. Skip rules funcionam conforme projetado

A fixture foi escolhida especificamente para exercitar o caminho de skip:

- `code-quality-reviewer` foi corretamente skipped por **ambas** as condições (`.md` + scope=docs)
- `spec-compliance-reviewer` foi corretamente **não** skipped (docs não está em nenhuma skip rule)

**Insight:** A skip rule `"scope == 'docs'"` para `code-quality-reviewer` é meio redundante com `"all_changed_paths endsWith .md"` em docs commits típicos. Mas ela protege casos onde scope=docs mas paths misturam (ex: doc + code no mesmo PR). Manter ambas.

### 2. `spec-compliance-reviewer` e `code-quality-reviewer` são aliases

A skill e a matriz referenciam `spec-compliance-reviewer` e `code-quality-reviewer` como reviewers, mas em `.agents/agents/` eles não existem como arquivos `.md` separados — `spec-compliance-reviewer` é alias para `code-reviewer` (per review-router.md §"Coordenação"). O lint NÃO valida refs em `always_on` nem em `skip_rules` (só em `path_globs`/`commit_types`/`diff_patterns`), então aliases passam silenciosamente.

**Gap conhecido:** O lint deveria talvez avisar (não erro) sobre aliases não mapeados para agentes reais. Não é bloqueador para o pilot, mas deve ser endereçado em Fase 4 (Memories).

### 3. Classifier não conhece skip rules

O classificador headless (`pnpm review:route`) retorna apenas os reviewers despachados **antes** da aplicação de skip rules. As skip rules são aplicadas pelo **agent** `review-router` (não pelo classificador). Isso é intencional (skip rules precisam de contexto de `task.scope` que vem do controller, não do diff), mas significa que:

- Output do classifier ≠ output final do router
- Documentação deve ser clara sobre essa distinção
- Workflows que usam só `pnpm review:route` (sem router agent) podem despachar reviewers em excesso

**Não bloqueador:** O workflow `monorepo-change.md` corretamente delega ao agent `review-router`, não ao classifier direto.

### 4. Fixture `docs(...)` é uma boa escolha para pilot

Critérios atendidos:

- 1 arquivo (suficiente para classificação significativa)
- 1 commit (suficiente para testar parser de conventional commits)
- Path que casa path_glob (dispara reviewer de domínio)
- Commit type `docs` (NÃO pula `spec-compliance-reviewer`)
- Arquivo `.md` (pula `code-quality-reviewer`)

Isso exercita 3 dos 4 caminhos lógicos críticos (always_on dispatch, always_on skip, domain dispatch). O 4º caminho (diff_pattern match) NÃO foi exercitado — para pilot run isso é aceitável; deve ser coberto em Fase 4 com uma segunda fixture que toque security ou nestjs decorators.

### 5. Latência 889 ms é dominada por cold-start do `tsx`

A execução real do classificador (regex + glob matching + YAML parse) é da ordem de poucos ms; os ~889 ms medidos incluem cold-start do `tsx loader`, parsing do `node_modules`, e I/O de leitura da matriz + paths file. Para workloads reais com diffs próximos do cap de 50 KB, espera-se latência similar (a regex é linear no tamanho do diff e o glob matching é O(patterns × paths)).

**Não bloqueador:** Mesmo com diff de 50 KB, latência esperada fica bem abaixo de 90 s.

## Gaps Identificados (para Fase 4 / 5)

1. **Aliases não validados pelo lint** — `spec-compliance-reviewer`, `code-quality-reviewer` passam silenciosos sem mapeamento explícito para `.agents/agents/*.md`. Adicionar warning (não erro) em `lint-review-routing.ts` v2.
2. **Pilot não exercitou `diff_pattern` match** — Adicionar uma segunda fixture em Fase 4 que toque bcrypt/jwt/secret/etc para validar o caminho `blocking: true`.
3. **`domains` sempre vazio** — O classificador popula `reviewers[]` mas nunca popula `domains[]` (que deveria ser `nestjs|prisma|nextjs|...`). Não bloqueador (consumidores usam `reviewers[]`), mas documentar no design.
4. **Skip rules aplicadas fora do classificador** — Considerar mover avaliação de skip rules para o classificador em v2 da matriz (com `task.scope` como input explícito do CLI), para tornar o pipeline mais testável headlessly.
