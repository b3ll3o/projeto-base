    * fix(docker): o ENTRYPOINT da api aponta para caminhos que a imagem não tinha
    
    A MEDIDA do #137 (o `docker stop` precisa alcançar o Node) mostrou que a
    imagem de produção **não subia**: o `COPY` do `prisma/` e do `scripts/`
    achata as DUAS pastas em `/repo/apps/api/`, e o ENTRYPOINT usa
    `prisma/schema.prisma` e `./scripts/prepara-papeis.sh` — nenhum dos dois
    existia.
    
    MEDIDO 2026-11-09, com a imagem de verdade (`docker buildx build --target
    prod`):
    
      $ docker run --rm --entrypoint sh projeto-api -c 'ls /repo/apps/api/'
      dist  node_modules  package.json  prisma  schema.prisma  seed.ts
      prepara-papeis.sh          # <- o CONTEUDO das duas pastas, achatado
    
    E o symptom era o do ENTRYPOINT inteiro:
    
      Error: Could not load `--schema` from provided path `prisma/schema.prisma`:
      file or directory not found
    
    O `COPY` com VÁRIAS origens copia o CONTEÚDO de cada uma direto para o
    destino — e o destino precisa ser um diretório. O conserto são DOIS `COPY`,
    um por pasta, com o nome preservado.
    
    ⚠️ Este defeito é de #128 (2026-10-27) e é anterior a este PR — e ele é a
    razão de o `exec` do #137 ser código morto até agora: a imagem não chegava
    ao ENTRYPOINT. O CI não via, porque o job `docker-build-prod` só CONSTRÓI a
    imagem (e `docker compose up` local usa o overlay de dev, cujo target é
    outro).
    
    ## A medição do #137, agora que a imagem sobe
    
    O critério de aceite da issue pede que o processo Node seja o filho DIRETO
    do init — é isso que faz o SIGTERM do `docker stop` chegar nele. MEDIDO nas
    duas formas, com a imagem de verdade:
    
      SEM o exec:                        COM o exec:
        pid=1   ppid=0  docker-init        pid=1   ppid=0  docker-init
        pid=7   ppid=1  sh -c …             pid=7   ppid=1  node dist/main.js
        pid=334 ppid=7  node dist/main.js
    
    Sem o `exec`, o node é um NETO do tini — e o tini repassa o sinal apenas ao
    filho DIRETO (o `sh`, porque o daemon não passa `-g`). O node nunca recebia
    o SIGTERM, o `enableShutdownHooks()` (main.ts:97) nunca rodava, e o
    container morria de SIGKILL no fim do grace period. Com o `exec`, o node é o
    filho direto — e o sinal chega nele.
    
    `docker stop -t 10`: 251 ms com o `exec` (o container não espera o grace).

    * fix(security): as duas camadas medem a MESMA senha, e o `***` é prefixo
    
    A revisão do PR #147 achou duas divergências entre a camada que ESCREVE a
    senha dos papéis e o guard que a julga — e as duas eram a mesma classe: as
    duas camadas NÃO mediam a mesma coisa.
    
    A primeira: o `prepara-papeis.sh` escapava o `'` (o único caractere que muda
    o sentido de um literal SQL) na LEITURA da URI, e o filtro media a senha
    ESCAPADA — enquanto o guard (TypeScript) media a senha CRUA. MEDIDO: uma
    senha de 12 bytes feita de aspas virava 24 bytes escapados, e o script
    APLICAVA o que o guard recusava (12 < 24). A camada que escreve era a mais
    frouxa das duas, e o invariante escrito no cabeçalho ("a MEDIDA tem de ser a
    MESMA nos dois lados") era falso.
    
    O conserto separa as duas coisas: a leitura devolve a senha CRUA (é a que o
    filtro mede, e a que o guard mede) e o escape passa a acontecer no `printf`
    do SQL, que é onde o literal é montado.
    
    A segunda: o `case` do shell casava `'***'` (entre aspas) como valor EXATO,
    enquanto o guard usa `startsWith` — PREFIXO. O script ACCEPTAVA `***` + 21
    bytes, valor que o guard classifica como exemplo: a isca que o script diz
    que não pode passar passava nele. O padrão virou `'***'*`.
    
    As duas têm spec agora (o harness roda o filtro no `sh` de verdade), e a
    spec do guard ganhou o caso dos bytes e o da troca de papéis.
    
    E o número que não batia: o `api-client.ts` dizia "11 lugares" quando a
    MEDIDA em `main` é 10 — e o 11º é o `sair` que este PR acrescenta. O
    `docs/web/rotas.md` também mostrava o literal, e agora aponta para a
    função.
    
    ⚠️ E uma lead que a revisão deixou em aberto, agora MEDIDA: o PR altera o
    SQL de uma migration JÁ APLICADA (`20261020000000_rls_isolation_empresa` —
    tira a senha publicada e põe o papel em `NOLOGIN`), e a migration tem o
    checksum velho no banco. Num Postgres 16 real, com um banco de rascunho que
    rodou as 16 migrations de `main` e depois recebeu as 18 de HEAD:
    `migrate deploy` sai **0**, sem `P3009` — o `deploy` não compara o
    checksum das migrations já aplicadas. O comando está na §Evidence do PR.
